## A. OOM while loading contacts (Crashlytics a5da4a8b99c4c5388a0edba5a2cae251)

### Evidence

- `OutOfMemoryError` at `ContactsRepository.queryAllContactsOrThrow` (:157,
  a 40-byte `getString`), growth limit 128 MB, "<1% of heap free after GC".
- Itel A665L, Android 13, 1.2 (135). Crash ~4 min into the session, on a
  provider-change reload (`mapLatest` frame), not on first load.
- The envelope catches `Exception`; `OutOfMemoryError` is an `Error`, so it
  reaches the crash handler.

### Root cause

`queryAllContactsOrThrow` buffers the **entire** `Data` table into an
`ArrayList<DataRow>` before aggregating:

- every row of every mimetype is kept, including rows the aggregator never
  reads (WhatsApp/Telegram profile+voip+video rows, group memberships, photos,
  IM, relations …);
- each row holds its own copies of `mimeType`, `accountType`, `accountName`,
  `displayName`, `photoThumbUri` (≈ 450–550 B/row retained);
- during a reload the previous list is still alive (SharedFlow replay cache +
  ViewModel state), then `groupBy` adds a second set of per-contact and
  per-raw-contact lists on top of the row buffer.

Peak ≈ old list + full row buffer + groupBy lists + new list. On a 128 MB heap
a large, messy address book (the audience of a dedupe app) exhausts it.

The dataset size of the affected device is unknown; the fix removes the
largest transient (the row buffer) and workstream B adds the counts needed to
see real dataset sizes in the field.

### Fix — stream rows into a compact accumulator

1. **Test first** (`app/src/test/.../data/`):
   - `ReferenceAggregator` (test source only): verbatim copy of today's
     list-based `ContactAggregator.aggregate` — the oracle.
   - `ContactAccumulatorTest`: seeded randomized differential test. ≥ 300
     iterations; each builds 0–60 random `DataRow`s and asserts
     `ContactAccumulator` fed row-by-row `==` `ReferenceAggregator.aggregate`.
     Generator must cover: several contacts, 1–3 raw contacts per contact
     (a raw id belongs to exactly one contact), all nine used mimetypes plus an
     unknown custom mimetype and `null`, `data1..data4` from a small pool with
     `null`, `""`, `"  "` and repeated values, multiple name/org/nickname/note
     rows per raw contact, event rows with `data2` in {"1","3","2",null},
     `displayName` null/blank/real, `photoThumbUri` null/non-null, contact-level
     columns (displayName, photo, starred) constant per contact.
   - Existing `ContactAggregatorTest` stays untouched and green.
2. **`ContactAccumulator`** (in `data/ContactAggregator.kt`):
   `fun add(row: DataRow)`, `fun build(): List<Contact>`, `val rowCount: Int`.
   Keeps only per-contact / per-raw-contact builder state — never the rows.
   Semantics identical to today's code:
   - contacts in first-appearance order, then stable
     `sortedBy { displayName.lowercase() }`; raw contacts in first-appearance
     order within their contact;
   - contact `displayName` = first row's value if not blank, else first phone
     of the first raw contact that has one, else first email likewise, else
     `"(unnamed)"`; `photoThumbnailUri` = first non-null; `starred` = first row;
   - raw `accountType`/`accountName` = first row of that raw contact;
   - name / organization / nickname / note: the **first** row of that mimetype
     wins even if its value is blank (`givenName`=data2, `familyName`=data3,
     `organization`=data1, `jobTitle`=data4, each `takeIf { isNotBlank() }`;
     `note` = first note row's data1 with no blank check);
   - birthday (`Event.TYPE_BIRTHDAY`) / anniversary (`Event.TYPE_ANNIVERSARY`):
     first event row whose `data2 == type.toString()` and `data1` not blank;
   - phones / emails / websites / addresses: rows with non-blank `data1`,
     distinct by `data1` (first wins), `LabeledValue(dataId, data1, typeLabel)`.
   - `accountType` / `accountName` are pooled (a `HashMap<String, String>`) so
     thousands of raw contacts share one instance per account.
   `ContactAggregator.aggregate(rows: List<DataRow>)` stays as a thin wrapper
   over the accumulator. Add `ContactAggregator.usesData(mimeType: String?)`
   (true for the nine mimetypes the aggregator reads).
3. **`ContactsRepository.queryAllContactsOrThrow`**: no `ArrayList<DataRow>`.
   Per cursor row build one transient `DataRow` and `add` it. Read
   `DATA1..DATA4` and compute `typeLabel` **only** when
   `ContactAggregator.usesData(mimeType)`; otherwise pass `null` (the row still
   registers its raw contact + account, so account membership — e.g. WhatsApp —
   is unchanged). Projection, selection, and the try/catch envelope unchanged.
   Do **not** catch `OutOfMemoryError` (an empty list would tell the user their
   contacts are gone and would feed empty snapshots to write paths).
4. `CHANGELOG.md` `## [1.3] - 2026-11-27` + `appVersionName=1.3`
   (`update-changelog` skill; `./gradlew -q changelogs` must print the entry).

Not in scope (noted for later): `HomeViewModel` runs `DuplicateFinder.find` on
every emission just for the badge count; `sortedBy { lowercase() }` allocates
per comparison. `android:largeHeap` is an optional extra mitigation — owner's
call, not part of this fix.

## B. Firebase Performance Monitoring

- **SDK only, no Gradle plugin.** `com.google.firebase:firebase-perf` via the
  existing BoM (`libs.versions.toml` → `firebase-perf`). The
  `firebase-perf` Gradle plugin only instruments HTTP calls / `@AddTrace`; this
  app has no network code of its own, so the plugin adds AGP-9 build risk for
  nothing. Automatic app-start, foreground/background and screen-rendering
  (slow/frozen frames) traces come from the SDK alone.
- **Collection off for debuggable builds**, next to the Crashlytics toggle in
  `ContactManagerApp` (`FirebasePerformance.getInstance().isPerformanceCollectionEnabled`).
- **Seam** (mirrors `Analytics`):
  - `domain/analytics/PerformanceTracer.kt` — pure Kotlin:
    `interface PerformanceTracer { suspend fun <T> trace(name: String, block: suspend TraceScope.() -> T): T }`,
    `interface TraceScope { fun metric(name: String, value: Long) }`,
    `object NoOpPerformanceTracer`, `object PerfTraces` (name constants).
  - `data/analytics/FirebasePerformanceTracer.kt` — starts a Firebase `Trace`,
    stops it only when the block returns normally (failed/cancelled work is not
    recorded); every Firebase call wrapped in `runCatching` — monitoring must
    never break a load.
  - `di/AnalyticsModule.kt` — provided with the same `FirebaseApp` guard,
    NoOp fallback.
- **Custom traces** (counts only — never contact data, same rule as analytics):
  - `contacts_load` around `ContactsRepository.loadContacts()`; metrics
    `data_rows`, `contacts`, `sim_contacts`.
  - `accounts_load` around `AccountRepository.getAccountsOrThrow()`; metric
    `accounts`.
- Docs: AGENTS.md (analytics line + a gotcha: no perf Gradle plugin, why).
  Not user-facing → no changelog entry.
- Owner follow-up (not code): Play Data safety + privacy policy must cover
  Performance Monitoring (diagnostics / performance data, Firebase
  installation ID).

## C. "New SIM contact not visible" (Umidigi A15C, Android 13)

### What the code and screenshots establish

- Returning to the app after > 10 s restarts the contacts pipeline
  (`WhileSubscribed(5_000)` in both the ViewModel and the repository), which
  re-reads `icc/adn`. So plain staleness does not explain a contact still
  missing four minutes later.
- The chip reads "SIM" with no slot number or carrier. That label appears only
  when (1) the icc fallback is in use — no `READ_PHONE_STATE`, so only
  `content://icc/adn`, i.e. the **default** subscription, is read — or (2) a
  native SIM account whose type cannot be mapped to a slot exists, in which
  case `IccSimAccountsIntegration.uncovered` disables every icc read and the
  app shows the OEM's ContactsContract mirror of the SIM.
- The other app tags each entry with a carrier ("Free") and the status bar
  shows two signal indicators — consistent with two SIMs.

### Candidate causes (not yet distinguishable)

1. **Dual SIM, phone permission not granted**: the new contact is on the
   non-default SIM, which the fallback never reads.
2. **Stale OEM mirror**: the app shows the ContactsContract copy of the SIM; a
   third-party write straight to the card does not update that copy until the
   SIM is reloaded (reboot).
3. `AccountClassifier` treats any account type containing "sim" as a SIM
   account; an unrelated account of that kind would also disable the icc read.

Each needs a different fix (enumerate subscriptions without the permission /
reconcile mirror with icc / tighten the classifier). Shipping one blind risks
double-listing SIM contacts on Samsung-class devices.

### Open decision

Ask the reporter three questions first (one SIM or two; does the contact appear
after a reboot; screenshot of Settings › Accounts), then implement the matching
fix. Whether C lands in 1.3 or a follow-up depends on the owner.
